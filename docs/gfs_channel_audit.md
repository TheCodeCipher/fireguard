## 4. Direction classification
- **GFS wind direction (band 20): `QUADRANT_LIMITED`**. all values within about [-90, 90] (min -90.00, max 90.00).
  - Share of values per sector (0-90, 90-180, 180-270, 270-360 degrees, taken mod 360): 0.557, 0.000, 0.000, 0.443.
- **GRIDMET wind direction (band 8): `FULL_CIRCLE`**. range spans 360.0 degrees (min 0.00, max 360.00) and all four 90-degree sectors hold >= 2% of values.
  - Share of values per sector: 0.105, 0.152, 0.439, 0.304.
- **Raw u/v components: NOT in the released rasters.** `compute_daily_features` returns only forecast wind speed and direction (derived from u/v inside Earth Engine); u and v are not exported. Direction cannot be rebuilt from anything else in the files.
- **Code trace versus data:** reading `FirePred.py` (u and v averaged over F01-F24, then `atan2(v, u)` converted to degrees) predicts a range of [-180, 180]. The data shows [-90, 90]. The stored channel therefore does not behave like a full-circle atan2. **Cause: UNKNOWN.** The measured data takes precedence over the code reading. Possible causes to check in Earth Engine: how `ee.Image.atan2` orders its arguments or handles quadrants, or a later transformation. This does not change the classification.
- **Loader effect:** the baseline applies `sin()` to angle channels and not `cos()` (data dictionary section 9). Sine alone cannot tell 30 degrees from 150 degrees, so even a full-circle channel loses information in the loader.

## 5. Do the GFS and GRIDMET direction conventions agree?
Paired pixels where both channels are finite; lower median circular difference = better fit. A random relationship gives about 90 degrees in the 360-degree column and about 45 in the 180-degree column.

| Hypothesis | 360-degree median diff | 360-degree mean | 180-degree (axis) median diff | 180-degree (axis) mean |
|---|---:|---:|---:|---:|
| gfs ~ 270 - th   (th = FROM, clockwise from N) | 42.6 | 59.3 | 32.3 | 36.8 |
| gfs ~ 90 - th    (th = TOWARD, clockwise from N) | 137.4 | 120.7 | 32.3 | 36.8 |
| gfs ~ th         (same convention) | 102.8 | 97.9 | 44.5 | 44.8 |
| gfs ~ th + 180   (opposite of same convention) | 77.2 | 82.1 | 44.5 | 44.8 |

- Verdict: NOT MEANINGFUL for the 360-degree column: the GFS channel is not full-circle, so it has lost half of the direction information and cannot be compared with GRIDMET as a direction. Use the 180-degree (axis) column instead, which ignores the lost sign.
- The convention of GRIDMET `th` should also be confirmed on its Earth Engine catalogue page (IDAHO_EPSCOR/GRIDMET). Until then treat it as UNKNOWN.

## 6. GFS timing trace (from `FirePred.py`)
Selection rule: the forecast images with index between `<YYYYMMDD>00F01` and `<YYYYMMDD>00F24`, i.e. the **00Z run of day D**, lead hours 1 to 24, averaged. The loader pairs inputs of day D with the fire target of day D+1 (data dictionary section 6).

| Question | Finding | Status |
|---|---|---|
| Which run? | 00Z run of day D | confirmed from code |
| Which valid times? | 01:00Z on D to 00:00Z on D+1 (F01 to F24) | confirmed from code |
| Level A (no look-ahead) | F24 is valid at 00:00Z on D+1, which is the start of the target day. It is 1 of 24 averaged fields, but the rule is "nothing at or after the start of the target day". Not a clean PASS. | UNKNOWN (borderline), needs Role 4 ruling |
| Level B (operationally available) | The 00Z run is published some hours after 00:00Z, and its F01 to F24 window covers time that has already passed on day D. Whether it counts as available depends on the forecast issue time the app assumes. | UNKNOWN |
| Is the day UTC? | The code uses UTC dates in the index and in `acq_date`; local-time shift is not handled | UNKNOWN, verify |

Remaining verification (Earth Engine Code Editor): print one image, for example
`print(ee.ImageCollection('NOAA/GFS0P25').filter(ee.Filter.eq('system:index','2018010600F24')).first());`
and record its creation/forecast time properties and the NOAA publication lag. Write UNKNOWN until you have seen them.

## 7. Other findings from the code (hand to Role 4)
1. **GFS precipitation definition changes on 2019-11-07.** Before that date the code sums hourly values; after it, it takes the last value (cumulative). The channel therefore means different things in 2018/early 2019 versus late 2019-2021. Per-year statistics below should show it if it matters. This matters for leave-one-year-out evaluation.
2. **GFS precipitation band is not renamed.** `forecast_rain.rename(...)` is called without assigning the result. Band order is unaffected (positional), but any name-based lookup would miss it.
3. **GFS wind speed is the speed of the 24-hour vector mean**, so it understates speed on days when the wind direction changes.
4. **VNP13A1 (NDVI/EVI2) window:** the code takes the last composite whose start lies in the 15 days up to the end of day D. A 16-day composite can extend past D. Needs Role 4's Level-A check.
