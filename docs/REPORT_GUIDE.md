# Report guide

What each section of the report should contain, and the exact file each number, table or figure
comes from. Every result file is regenerated by `python scripts/train_all.py`; quote numbers from
the files, never from memory.

## 1. Introduction and task

- Task: for a fire burning on day D, predict for every 375 m cell the probability of a VIIRS
  active-fire detection on day D+1 (24-hour horizon).
- Why it is hard: positives are 0.07-0.28 % of cells (per test year: `docs/evaluation/baseline_results.md`),
  so accuracy is meaningless and AUPRC is the headline metric.
- Scope: western-US fires 2018-2021 (WildfireSpreadTS); a research forecast, not a warning system.

## 2. Data

| Fact | Value | Source |
|---|---|---|
| Dataset | WildfireSpreadTS v1.0: 607 events, 13,607 daily GeoTIFFs, 23 bands, 375 m, EPSG:32610 | `configs/data/strict_input_v1.yaml`, `docs/data/data_dictionary.md` |
| Scored samples | 10,572 (event, day) pairs, identical for every model | `data/manifests/wsts_eval_samples.csv` |
| Inputs used (7) | VIIRS M11, I2, I1 reflectance; slope, sin(aspect), elevation; day-D active-fire mask | `configs/models.yaml` |
| Excluded inputs and why | GFS forecasts, gridMET weather, drought index, NDVI/EVI2, year-Y land cover: they may contain information from after day D (no-look-ahead audit) | `docs/data/leakage_audit.csv`, `docs/data/leakage_audit_notes.md`, `docs/data/gfs_channel_audit.md` |
| Target | band 23 (active fire) of D+1, NaN -> 0, > 0 | `configs/data/strict_input_v1.yaml` |
| Preprocessing | per-fold standardisation from training fires only; missing values -> training mean; frames padded to a multiple of 32 and padding masked | `ml/src/fireguard_ml/training/normalization.py` |

## 3. Evaluation protocol

- Leave-one-year-out (P1): each of 2018-2021 is the test year once; validation is about 17.5 % of the
  remaining fire-complex groups; the rest train. Related fires (overlapping or within 30 km and 14
  days) form one group and never straddle a split. Manifest hash `34e29090...`, frozen.
  Sources: `docs/evaluation/evaluation_protocol.md`, `docs/data/fire_complex_groups.md`,
  `data/manifests/p1_loyo_fold_manifest.csv`.
- Metrics: pooled and event-macro AUPRC (primary); F1 and IoU at the validation-chosen threshold;
  Brier, Brier skill score vs climatology, ECE (after Platt calibration fitted on validation).
  Source: `docs/evaluation/metrics_contract.md`.
- Comparisons: paired bootstrap over fire-complex groups (2,000 replicates, 95 % interval); per fold
  BETTER / WORSE / NO_DIFFERENCE_SHOWN; gate rules in `docs/evaluation/model_comparison_protocol.md`.
- Model selection: highest mean validation AUPRC over the four folds; the test years never choose
  the model.
- Caveat to state: 2019 has the fewest fires (88 test events); do not let it decide anything alone.

## 4. Baselines

Persistence, dilated persistence, distance-to-fire decay, distance-bin climatology (fitted on
training fires only). Table: `docs/evaluation/baseline_results.md`. Strongest baseline per fold
(chosen on validation): `results/comparison/model_comparison.md`.

## 5. Models

Describe each with one paragraph and one diagram; details are in the docstrings of
`ml/src/fireguard_ml/models/architectures.py`.

| | Inputs | Architecture | Parameters |
|---|---|---|---|
| M1 | day D | U-Net, depth 5, base width 32, two 3x3 conv + GroupNorm + ReLU per block, max-pool down, transposed-conv up, skip connections, 1x1 head | 8.36 M |
| M2 | day D | M1's layout with residual blocks and additive attention gates on every skip connection | 8.86 M |
| M3 | days D-4..D | M1's U-Net with the 5 days stacked on the channel axis (35 input channels) | 8.36 M |
| M4 | days D-4..D | one encoder shared by all days; ConvLSTM (3x3) over the 5 days at the 1/32 and 1/16 levels; finer skips from day D; same decoder | 17.79 M |

Explain the ladder: each step changes one thing (M2 vs M1 architecture, M3 vs M1 history, M4 vs M3
recurrence). Explain why plan v4's M2 (terrain + land cover) was replaced: land cover fails the
leakage audit and terrain is already in every model (`docs/evaluation/phase_gate_log.md`,
2026-11-14 entry). Exact parameter counts per run: `results/metrics/training_runs.csv`.

## 6. Training

| Setting | Value | Why |
|---|---|---|
| Loss | masked BCE + soft Dice | BCE for per-cell probabilities, Dice against the extreme imbalance (plan v4 4.6) |
| Optimiser | AdamW, peak lr 1e-3, weight decay 1e-4 (not on norms/biases) | standard for U-Nets |
| Schedule | 1 epoch linear warm-up, cosine decay to 1e-5 | stable start, smooth convergence |
| Batch | effective 16 samples per update (GPU batch x gradient accumulation, chosen per GPU) | same optimisation on any hardware |
| Regularisation | spatial dropout 0.1 at the bottleneck, weight decay, horizontal/vertical flips (sin(aspect) negated on E-W flips) | ~600 fires and strongly correlated days overfit easily |
| Precision | bfloat16 autocast on the GPU | speed and memory |
| Early stopping | validation AUPRC on full frames at natural prevalence, patience 6, max 40 epochs, best epoch kept | plan v4 6.2 |
| Calibration | Platt scaling and F1 threshold fitted on validation fires per fold | `ml/src/fireguard_ml/evaluation/calibration.py` |

Hardware actually used, minutes per fold and best epochs: `results/metrics/training_runs.csv`.
Learning curves: `results/figures/03_training_curves.png`.

Worth a paragraph on what went wrong first: the first M1 run (fold 2018) peaked at its second
epoch and plateaued. Causes found: samples ordered fire by fire (consecutive updates from one
fire), batch size 1 with a constant learning rate, patience 3 on a noisy validation curve, and the
GPU mostly idle while GeoTIFFs were decoded. The fixes are the settings in the table above plus the
array cache.

## 8. System

- Replay lab: held-out forecast first, observed fire revealed after; leakage rules in
  `docs/contracts/reveal_contract.md`. Screenshot it from the running site (docs/RUNBOOK.md section 3).
- Live: daily forecast with the selected model from NASA FIRMS detections and Earth Engine
  terrain/reflectance, next to the FIRMS detections (docs/RUNBOOK.md section 4). Input checks:
  `docs/evidence/live/live_input_parity.json`, `docs/evidence/live/live_hindcast.json`; running
  live scores: `artifacts/live/live_scores.csv`.
- Architecture of the software: backend (FastAPI, retrieve-only), frontend (React + MapLibre),
  offline ML package; `README.md` has the map.

## 9. Limitations

- Target is a satellite detection: clouds and smoke hide fire, so "no detection" is not "no fire"
  (`docs/history/reports/observability_and_label_quality.md`).
- No weather inputs in the strict models (timing could not be verified), which caps skill for
  wind-driven spread.
- Western US only, 2018-2021; reflectance in live use comes from a newer VIIRS collection, mapped
  to the old scale.
- Probabilities come from an average of four fold models; their spread is not an uncertainty
  estimate.

## 10. Future work

1. **Dilated ConvLSTM.** Replace the 3x3 ConvLSTM gates with dilated convolutions (or stack
   ConvLSTM layers with increasing dilation) so the temporal memory covers a wider area at fine
   resolution without more pooling. That lets fast runs of several cells per day be tracked at the
   1/4-1/8 levels, where the current M4 only has day-D features.
2. **Transfer learning to other regions.** Where a region lacks enough labelled fire history,
   start from the encoder trained here and fine-tune on the little local data available
   (optionally freezing the early layers), with the same leave-one-year-out testing in the new
   region. This needs the region's inputs rebuilt with the same recipe (VIIRS reflectance, SRTM
   terrain, VIIRS active fire), which the live pipeline already does for any area.
3. Weather inputs once their timing passes the audit (`docs/data/gfs_branch_gating.md`).
4. Seeds: repeat the selected model with 3 seeds to separate model differences from training noise.
